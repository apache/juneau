`juneau-rest-server-views` is the browser-side toolkit behind the console's table cards: a server-driven table
view with search, sort, paging, a column chooser, saved View Settings, row actions, bulk mutation, cell popovers,
row-detail regions, async-job streaming and shareable links. The server describes a view with plain beans and
annotations; a first-party JavaScript runtime (`juneau-views.js` and its companions) draws it.

Most adopters never touch the view beans directly. You author a `<@card type="datatables">` catalog in a
FreeMarker template (see [Building a Console Page](/docs/topics/BuildingAConsolePage)) and the chrome lifts it into
the view contract for you. This section documents what that catalog can express, the security model behind it, and
the `JuneauViews` JavaScript API for pages that need to go further.

## Modules and mixins

| Module | Mixin / class | Serves |
|---|---|---|
| `juneau-rest-server-views` | `ViewsMixin` | `/juneau-views.js`, `-renders.js`, `-icons.js`, `-search.js`, `-pagestate.js`, `-urlstate.js`, `-ribbon.js`, `-regions.js`, `-helpers.js`, `-config.js`, the CSS, and the symbol sprites. |
| `juneau-rest-server-views` | `AsyncJobsMixin` | `/juneau-jobs/{jobId}/stream` and `/juneau-jobs/{jobId}/cancel`. |
| `juneau-rest-server-datatables` | `DataTablesMixin` | `/juneau-datatables.js`, the browser glue for server-side processing. |

:::warning The host must compose DataTablesMixin
A server-mode table (one whose catalog says `dataMode: "server"`) is driven by `juneau-datatables.js`, which is
served by `DataTablesMixin` from `juneau-rest-server-datatables`, not by `ViewsMixin`. The `views` toolkit pack
lists that script ahead of `juneau-views.js` when the page has a server-mode datatables card. If the host does not
compose `DataTablesMixin`, the script 404s and the table fails loudly (console warning, no silent GET fallback).
A host whose pages have no server-mode table does not need it. See
[DataTables Server-Side Processing](/docs/topics/DataTables).
:::

```java
@Rest(
	path="/console",
	mixins={ViewsMixin.class, ConsoleChromeMixin.class, DataTablesMixin.class}
)
public class ConsoleResource extends BasicRestServlet {}
```

## Contract versions

The toolkit has three independent, versioned wire contracts, plus the page contract owned by the chrome. Each one
is checked separately, and a mismatch fails loudly rather than degrading silently.

| Contract | Key | Current | Owner | Constant |
|---|---|---|---|---|
| Page contract (JSON island `#juneau-page`) | `contractVersion` | `"1"` | `PageCapture` / `juneau-console.js` | `PageCapture` writes it; see [Admin-Console Chrome](/docs/topics/AdminConsoleChrome) |
| View metadata (`VIEW_META` sidecar) | `contractVersion` | `"5"` | `ViewsMixin` | `ViewsMixin.CONTRACT_VERSION` |
| Card slot envelope (`SLOT_META`) | `contractVersion` | `"1"` | `ViewsMixin` | `ViewsMixin.SLOT_CONTRACT_VERSION` |
| Bar envelope | `contractVersion` | `"1"` | `ViewsMixin` | `ViewsMixin.BAR_CONTRACT_VERSION` |

Regions carry their own `RegionDef.CONTRACT_VERSION` (`"1"`), independent of all of the above.
`ViewsMixin.HEADER_CONTRACT_VERSION` is also `"1"`. `ActionResult` and `BulkMutateDef` carry their own
`CONTRACT_VERSION` (`"1"` each) for the action-result and bulk-mutate wire shapes.

### Omit and inject

You do not write any of these numbers by hand. When a `<@card type="datatables">` catalog is lifted into the
contract, the chrome injects the current `VIEW_META` and slot versions for you; a catalog should omit
`contractVersion` entirely. The one exception is an escape hatch: a catalog object that already carries both
`contractVersion` and a `view` block is treated as a pre-built slot envelope and passed through unchanged, so
whoever writes one owns its version numbers.

:::note
Automatic detection of a catalog that pins a stale `contractVersion` (a warn or fail-on-mismatch at render time)
is planned but not yet shipped. Today the safe practice is simply to omit the key.
:::
