The NG `RestClient` protects outbound calls against server-side request forgery (SSRF) and credential
leaks across redirects. This page describes what is enforced, where, and how to opt out. The same
URL policy class (`org.apache.juneau.http.remote.RemoteUrlPolicy`, in `juneau-rest-common`) is shared
with the classic client.

:::info Which calls are covered?
The SSRF guard (URL deny-list, pin-on-connect, per-hop redirect re-validation) applies to
**policy-covered** calls: `@Remote` / `@RemoteOp` proxies and dynamic `@Url` arguments, or a request
where you called `remoteUrlPolicy(true, ...)`. An ordinary `client.get("https://...")` is treated as
trusted application code and is not run through the deny-list.
:::

## URL policy

`RemoteUrlPolicy.requireAllowedUrl(url, allowPrivate)` rejects a URL unless:

- the scheme is `http` or `https` and the host is non-empty;
- the host is not on the deny-list: `localhost`, `localhost.localdomain`, `metadata.google.internal`
  (and its subdomains), or an IP literal that is loopback, any-local, link-local, site-local (RFC 1918),
  IPv6 unique-local (`fc00::/7`), IPv4 `0.0.0.0/8` ("this network"), IPv4 `100.64.0.0/10` (carrier-grade NAT
  shared space), IPv6 Teredo (`2001::/32`) or IPv6 local-use NAT64 (`64:ff9b:1::/48`). The last two are denied outright, because the
  embedded IPv4 address is obfuscated or its embedding length is operator-defined. IPv6 addresses that embed an IPv4 address
  (IPv4-mapped, IPv4-compatible, IPv4-translated `::ffff:0:a.b.c.d`, NAT64 `64:ff9b::/96`,
  and 6to4 `2002::/16`) are unwrapped and classified by the embedded IPv4 address. IPv6 zone ids
  (`[fe80::1%25en0]`) are ignored for classification, and an unparseable IPv6 literal is denied.

Relative values pass through, and the client's `rootUrl` is not re-checked. Bare decimal, octal, or hex
IP spellings are not recognized as literals by the string check; they are caught by DNS pinning below.

Set `allowPrivateUrls(true)` on the builder, `allowPrivateUrls=true` on `@Remote` / `@RemoteOp`, or the
system property `RestClient.allowPrivateUrls=true` to permit private addresses (for example, when
calling internal services). The effective setting is the logical OR of the three.

## DNS pinning

A host-name check alone is defeated by DNS rebinding and by names that resolve to private addresses.
When the guard is active, each transport resolves the host itself, picks the first address that is
*not* denied (`RemoteUrlPolicy.selectAllowedAddress`), and connects to exactly that address. If every
candidate is denied, the call fails with `TransportException`.

| Transport | Pinning mechanism |
|---|---|
| JDK `JavaHttpTransport` (default) | Rewrites the request URI to the pinned literal address and keeps the original `Host` header. It fails closed if pinning is not possible. |
| Apache HttpClient 4.5 | `PolicyPinningDnsResolver` on a dedicated policy-only client with its own connection pool. |
| Apache HttpClient 5 | `PolicyPinningDnsResolver` on a dedicated policy-only client with its own connection pool. |
| OkHttp | `PolicyPinningDns` on a dedicated policy-only derived client (shares the connection pool and dispatcher with the normal client, but OkHttp only reuses a connection for a request with the same `Dns`). |
| Jetty | `PolicyPinningSocketAddressResolver` |

Pinning is scoped to policy-covered requests, so normal traffic through the same client is unaffected,
and a policy-covered request never reuses a connection that a normal request opened without the pin.
The Apache HttpClient 4.5 and 5 transports send policy-covered requests through a second client of
their own, whose separate connection pool resolves every connection through the pin. Jetty tags
policy-covered requests, which gives them a separate connection pool of their own, and its resolver
pins every connection opened for that pool. OkHttp's policy-only client shares the normal client's
connection pool, but OkHttp reuses a connection only for a request with the same `Dns`, so the two
never share a connection.

### Transports that cannot enforce the policy

If the guard is active and the transport reports `supportsUrlPolicy() == false`, `RestRequest.run()`
refuses to send the request and throws `TransportException` ("Refusing to send a policy-covered
@Remote request..."). All bundled transports and the mock transports support the policy. The Apache
HttpClient 4.5, Apache HttpClient 5, and Jetty transports support it only with the client they create
themselves; built with a caller-supplied client, they report `supportsUrlPolicy() == false`. The OkHttp
transport reports `false` for a client with an explicit proxy, and refuses a policy-covered request that
the client's proxy selector routes through a proxy, because the proxy resolves the target host itself. A custom
[`HttpTransport`](/docs/topics/HttpTransportAdapters) must override `supportsUrlPolicy()` once it
implements pinning and honors `TransportRequest` redirect handling.

### Classic `RestClient`

The classic client (`org.apache.juneau.rest.client.classic.RestClient`) guards `@Remote` calls with the
same URL policy. The connection manager it builds keeps two separate pools: policy-covered calls lease
from a pinned pool whose connections are all opened through `PolicyPinningDnsResolver`, and every other
call leases from the ordinary pool. So a policy-covered call, or any of its redirect hops, never reuses
a connection that an ordinary call opened without the pin. This holds for both the default and the
`pooled()` connection manager. The pinned pool uses the ordinary pool's settings (pool limits, socket and
connection configuration), so a `createConnectionManager()` override that configures the manager returned
by `super` configures policy-covered calls too.

The connection manager the classic client builds applies the builder's TLS and pool settings to both
pools: `sslContext(...)` (for example one with a custom trust store), `sslHostnameVerifier(...)`,
`sslSocketFactory(...)`, `maxConnTotal(...)` and `maxConnPerRoute(...)`. Apache `HttpClientBuilder`
ignores its own copies of these once a connection manager is set. `maxConnTotal(...)` or
`maxConnPerRoute(...)` makes the connection manager a pooling one, as `pooled()` does. Each `build()`
creates a new connection manager, so a builder reused after `build()` gives every client its own, and
closing one client does not break the next. A connection manager you supply with `connectionManager(...)`
is used as is and keeps its own TLS and pool settings.

A custom `sslSocketFactory(...)`, or a socket factory set with `setSSLSocketFactory(...)` on the
`HttpClientBuilder` you pass to `httpClientBuilder(...)`, is also used for policy-covered calls. The pin hands
it the address it has already checked, and the factory must connect to exactly that address. A factory that
ignores that address and connects by host name, resolving the name again, bypasses the pin.

The other settings Apache `HttpClientBuilder` applies only to a connection manager it builds itself reach
both pools too: `defaultSocketConfig(...)`, `defaultConnectionConfig(...)`, `connectionTimeToLive(...)` (which
also makes the connection manager a pooling one) and `publicSuffixMatcher(...)` (used by the default hostname
verifier). So do TLS and pool settings made directly on the `HttpClientBuilder` you pass to
`httpClientBuilder(...)`, and the system properties `useSystemProperties()` reads: the JVM's default SSL
socket factory (the `javax.net.ssl.*` trust and key stores), `https.protocols`, `https.cipherSuites` and,
unless `http.keepAlive` is `false`, the `http.maxConnections` limit. A DNS resolver set on the
`HttpClientBuilder` is used for ordinary calls only; policy-covered calls always resolve through the pin.

If `httpClientBuilder(...)` replaces the `HttpClientBuilder` after you have configured the client builder, these
connection-manager settings made with the client builder's own setters carry over, and win over the same
setting on the replacement: `sslContext(...)`, `sslSocketFactory(...)`, `sslHostnameVerifier(...)`,
`publicSuffixMatcher(...)` (for the default hostname verifier only; its use for cookies is lost with the
replaced builder), `maxConnTotal(...)`, `maxConnPerRoute(...)`, `pooled()`, `connectionTimeToLive(...)`,
`defaultSocketConfig(...)`, `defaultConnectionConfig(...)` and the TLS and `http.maxConnections` system
properties of `useSystemProperties()`. Every other setting made before the replacement (interceptors, proxy, the
rest of `useSystemProperties()`, and so on) was made on the replaced `HttpClientBuilder` and is lost. For these
connection-manager settings, a value set with the client builder's own setter always wins over the same setting on
the `HttpClientBuilder`, whichever was set last: unlike Apache's last-write-wins, a later
`httpClientBuilder().setDefaultSocketConfig(...)` does not override an earlier `defaultSocketConfig(...)`. As in
Apache `HttpClientBuilder`, a socket factory wins over an SSL context wherever each was set, so a
`setSSLSocketFactory(...)` on the replacement wins over an earlier `sslContext(...)`.

`close()` shuts down the connection manager the client built for itself, even with
`connectionManagerShared(true)`: nothing else can reach it. "Shared" keeps open a connection manager you
supply, and any connection manager an overridden `createConnectionManager()` returns, even one that calls
`super`, because the override may hand the same instance to several clients.

The classic client refuses a policy-covered `@Remote` call ("Refusing to send a policy-covered @Remote
request...") when it cannot guarantee the pin. It cannot pin a connection manager it did not build, or a
call that goes out through an `HttpClient` other than the one it wired to its pinning connection manager.
The guard travels on the request's `HttpContext` (each redirect hop gets a context marked for the guard), so
it holds on whichever thread runs the request. A replaced call path may still send a copy of the request, or
send it with another context, so the refusals below are what keep such a path from going out unpinned. That
is the case when:

- you supply a connection manager with `connectionManager(...)`;
- you override `createConnectionManager()` to return a different one;
- you supply an `HttpClient` with `httpClient(...)`;
- you override `createHttpClient()` to return a different client, or a wrapper around the one `super`
  builds;
- you pass `httpClientBuilder(...)` (or return from `createHttpClientBuilder()`) an `HttpClientBuilder`
  subclass that overrides `build()`, `createMainExec(...)`, `decorateMainExec(...)` or
  `decorateProtocolExec(...)`, or inherits such an override. Any of these can build the client around
  another connection manager or request executor, even when `build()` returns the client `super` built;
- you set an `HttpProcessor` with `httpProcessor(...)`. It replaces all of the client's request interceptors,
  among them the guard's own and the redirect credential guard. Add interceptors with
  `addInterceptorFirst(...)` or `addInterceptorLast(...)` on the `HttpClientBuilder` instead;
- you set a custom `RestCallHandler` with `callHandler(...)`, or a `BasicRestCallHandler` bound to a different
  client;
- you use a `RestClient` subclass that overrides `run(HttpHost,HttpRequest,HttpContext)`,
  `execute(HttpHost,HttpRequest,HttpContext)` or `execute(HttpUriRequest,HttpContext)`;
- `createRequest(...)` returns a `RestRequest` subclass that overrides `run()`;
- an override of `createRequest(...)` or `request(...)` returns a `RestRequest` bound to a different client.
  That request would go out through the other client's `HttpClient`.

A policy-covered request whose `HttpContext` lacks the guard marker, for example one a custom call path sent
with a fresh context, is refused rather than sent unguarded. So is one that would open or reuse a connection
of the ordinary pool. That can only happen when the guard's request interceptor did not run, for example a
request with the guard's context sent directly through `execute(...)` on a client with an `HttpProcessor`.
A refused request leaves nothing behind: the next ordinary request on the same thread is sent normally.

A policy-covered call on a proxy route is refused too, because the pin would check the proxy's address
instead of the target's. This covers `proxy(...)`, a `routePlanner(...)` that picks a proxy, and the
proxy system properties read by `useSystemProperties()`. The refusal is reported as a `RestCallException`,
with the connection manager's `IllegalStateException` as its cause.

Ordinary calls are unaffected. Set `allowPrivateUrls(true)` if the target is an intentional local or
intranet service. `MockRestClient` supplies its own connection manager, so its `@Remote` calls need
`allowPrivateUrls(true)` too.

## Redirect re-validation

For policy-covered calls, Juneau runs the redirect loop itself (`PolicyEnforcedRedirects`) and turns
off the transport's own auto-redirect. For every `Location` hop:

1. the target URL is re-checked against the URL policy;
2. the hop is sent over a pinned connection;
3. on the classic client, a hop to another origin (or an https-to-http downgrade) drops the caller-set
   credential headers (the `RedirectSecurity` set described below). They stay dropped for the rest of the
   chain, even if a later hop returns to the first origin.

Handled status codes are 301, 302, 303, 307, and 308. 301/302/303 rewrite the method to `GET` and drop
the body (unless it was already `GET`/`HEAD`); 307/308 preserve the method and body. The call fails if:

- the redirect has no `Location`;
- more than 5 hops are followed (`RemoteUrlPolicy.MAX_REDIRECT_HOPS`);
- the `Location` is invalid, or names a host that `java.net.URI` cannot parse (such as `my_service`), so
  the origins cannot be compared;
- a 307/308 would have to replay a non-repeatable body (fail closed);
- the JDK `HttpClient` was configured to follow redirects itself (`Redirect.NEVER`, the default, is required).

Each of these failures, like a refused pin, is a `TransportException`.

## Credential stripping on redirects

When a redirect changes origin, credentials must not follow it. `RedirectSecurity` defines the rule:

- *same origin* compares scheme, host (case-insensitive), and port (80/443 normalized);
- credentials are stripped when the origin differs **or** the redirect is an https-to-http downgrade;
- the stripped set is `RedactedHeaders.DEFAULT`: `Authorization`, `Cookie`, `Set-Cookie`, `Proxy-Authorization`, and `X-API-Key`. The OkHttp transport keeps `Proxy-Authorization` only while the redirected request is still plain HTTP through the same HTTP proxy as the original request (the header authenticates you to the proxy, so stripping it there makes the proxy answer `407` again). With no proxy, a different proxy, or an `https` target (reached through a `CONNECT` tunnel), it is stripped like the rest;
- if the two origins cannot be compared, the guard strips (fail safe).

Transports apply this rule through `RedirectSecurity` when a redirect is followed. The OkHttp and Apache
HttpClient 4.5 transports compare origins on the library's own host object, so a host name that
`java.net.URI` cannot parse (for example the underscore name `my_service`) is compared like any other
host. The transports apply the rule on the clients they create; the OkHttp transport also applies it to a
client you supply. On OkHttp the origin is the first request after your application interceptors (so an
interceptor that rewrites the URL sets the origin), and only the values you sent are stripped: cookies
loaded from the client's `CookieJar` for the new origin, and credentials from its `Authenticator` or
`proxyAuthenticator`, still go to the new origin.

:::warning
A client you supply to the Apache HttpClient 4.5, Apache HttpClient 5 or Jetty transport follows ordinary
(non-SSRF-guarded) redirects with that library's own header handling, not this rule:

- **Apache HttpClient 4.5** copies the original request headers onto the redirect, so a caller-set
  `Authorization`, `Cookie` or `X-API-Key` **is sent to the cross-origin target**.
- **Apache HttpClient 5** (5.6, `DefaultRedirectStrategy`): when the redirect replays the original
  request's headers (a `307`/`308`, a `301`/`302` for any method except `POST`, or a `303` for `GET` or
  `HEAD`), it does not follow a cross-origin redirect that carries `Authorization`, `Cookie` or a header
  marked sensitive; you get the `3xx` response instead. Other headers, such as `X-API-Key`, are copied to
  the new origin. A `POST` redirected by `301`/`302`, or any method other than `GET` or `HEAD`
  redirected by `303`, is followed as a new `GET` that carries none of your headers.
- **Jetty** drops `Authorization`, `Cookie` and `Proxy-Authorization` on every redirect, including
  same-origin ones, but copies `X-API-Key`.

To get this rule on those transports, let the transport create the client.
:::

## Stale-connection retry

Keep-alive connections that the server closed while idle fail on reuse. The JDK, Apache HttpClient 4.5,
and Jetty transports detect that specific failure and replay the request **once** on a fresh
connection. A failure counts as stale when it is an `EOFException`, `ClosedChannelException`, a
connection-reset `SocketException`, or the JDK client's "received no bytes" message
(`TransportException.isStaleConnectionFailure`).

The replay is only attempted when `TransportRequest.isSafeToReplay()` is true: an idempotent method
(`GET`, `HEAD`, `PUT`, `DELETE`, `OPTIONS`, `TRACE`) and a body that is absent or repeatable. A `POST`
is never replayed by this mechanism.

This is separate from the `@Remote(retries=...)` policy retries described in
[Next-Generation REST Client](/docs/topics/NextGenRestClient), which retry on application-visible
failures according to your configuration.
