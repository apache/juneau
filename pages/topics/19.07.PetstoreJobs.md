The Jobs page, served at `/console/ops/jobs`, is the petstore's reference for **asynchronous work**. A restock adds
new pets in the background: the browser submits it once, the server answers `202` with a job reference, and the page
follows the job's progress until it settles. The page also hosts a terminal demo, a "groom pet" job whose output is
streamed into a terminal card. If a write in your app takes longer than a request, copy this page.

## What this page shows

- **The mixin.** `JobsRest` implements `AsyncJobsMixin` and `TerminalMixin`. `AsyncJobsMixin` serves the stream and
  cancel operations under `/juneau-jobs`; the resource supplies the `AsyncJobRegistry` through `asyncJobRegistry()`.
- **Submit once.** `POST /console/ops/jobs/restock` builds an `IdempotencyKey` from the body's `idempotencyKey` and
  calls `AsyncJobRegistry.tryCreate(key)`. A resubmit with the same key returns the same job, so the resource keeps no
  key map of its own.
- **Self-targeted keys.** The ribbon "Restock" dialog has no row to bind a key to, so `restockForm()` returns a
  `ModalDef` carrying `IdempotencyKey.mintSelfTargeted("restock")` and the `selfTargeted` flag. The two must travel
  together; see [Rich Table Views: Actions](/docs/topics/RichTableViewsActions) for the pairing rule.
- **Completion.** The job finishes with a success `ActionResult` (`ActionResult.success(null)`, which
  `ActionResult.ok()` is the readability alias for) and a message such as "Restocked 3 pets".
- **A job-log card.** The "Restock inventory" card is a `job-log` card: a small submit form (counts per species, plus
  two timing knobs) that posts the same restock in its flat form, shows the job's progress lines and offers Cancel.
  `slowMs` waits before touching the store, so a cancel changes nothing; `holdMs` holds after the pets are added, so a
  late cancel reports that the change was made.
- **A per-instance hard timeout.** The registry's hard timeout is 30 seconds. A host overrides it by declaring a
  `JobsRest.HardTimeout` bean, which is per resource instance, so one test host's short timeout does not leak into
  another. A job that exceeds it settles with `unknown` and `app:hard-timeout-exceeded`.
- **A concurrency limit.** At most two restocks run at once (system property `petstore.jobs.limit`; the registry's own
  cap is 8). A replay of an existing key never counts against the limit. When the limit is hit the server answers
  `429` with the refusal `app:job-limit`, and the message names the running count.
- **A terminal card.** The groom job (`GroomRuns`) streams its output through `TerminalMixin`, shown twice: a card over
  the in-memory output and a second over the same run's file-backed transcript.

## Template

The template is `jobs.ftlh`. The `job-log` card is configured entirely by its `submit` block.

```
<@card type="job-log" id="restock" title="Restock inventory">{
  submit: {
    endpoint: '/console/ops/jobs/restock',
    submitLabel: 'Restock',
    fields: [
      { name: 'DOG', label: 'Dogs (0-50)', type: 'number', default: 1 },
      { name: 'slowMs', label: 'Wait before restocking (ms, 0-10000)', type: 'number', default: 0 },
      { name: 'holdMs', label: 'Hold after restocking (ms, 0-10000)', type: 'number', default: 1000 }
    ]
  },
  urlParam: 'job'
}</@card>
```

## Builder twin

`OpsPageBuilders.jobs` takes the two `TerminalDef` values and builds the same cards.

```java
.card(CardSpec.of("job-log", "restock").title("Restock inventory")
    .body("submit", Map.of("endpoint", "/console/ops/jobs/restock", "submitLabel", "Restock", "fields", List.of(
        Map.of("name", "DOG", "label", "Dogs (0-50)", "type", "number", "default", 1),
        Map.of("name", "holdMs", "label", "Hold after restocking (ms, 0-10000)", "type", "number", "default", 1000))))
    .body("urlParam", "job"))
.card(CardSpec.of("terminal", "groom-output").title("Groom run").body("terminal", groomOutput.toMap()))
```
