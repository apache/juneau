A row action normally returns a terminal `ActionResult`. When the write is asynchronous, the same `POST` instead
returns an `AsyncJobRef`, and the runtime streams the job's progress to the browser over Server-Sent Events. Nothing
about the `RowAction` declaration changes; the runtime switches to the streaming path purely because the 2xx body
contains a `streamUrl`.

## Wiring it up

Compose `AsyncJobsMixin` and supply a registry:

```java
@Rest(path="/console", mixins={ViewsMixin.class, AsyncJobsMixin.class})
public class ConsoleResource extends BasicRestServlet implements AsyncJobsMixin {

	private final AsyncJobRegistry jobs = new AsyncJobRegistry();

	@Override
	public AsyncJobRegistry asyncJobRegistry() { return jobs; }
}
```

The mixin serves two operations under `AsyncJobsMixin.JOBS_PREFIX` (`/juneau-jobs`):

| Operation | Path | Behavior |
|---|---|---|
| `GET` | `/juneau-jobs/{jobId}/stream` | Replays buffered progress (so a page reload re-attaches), streams live `progress` events, then sends one `result` event carrying the terminal `ActionResult`, and closes. Unknown id is `404`; a job at its subscriber cap is `429`. |
| `POST` | `/juneau-jobs/{jobId}/cancel` | Cancels the job. |

## Starting a job from an action

```java
@RestPost(path="/incidents/{id}/reindex")
public AsyncJobRef reindex(@Path("id") String id) {
	var job = jobs.create();                 // or jobs.create(IdempotencyKey) to de-duplicate
	executor.submit(() -> {
		job.progress("Starting...\n");
		// ... do the work ...
		job.complete(ActionResult.ok());
	});
	return AsyncJobRef.of(job);
}
```

`AsyncJobRef` carries `jobId`, `streamUrl` and `cancelUrl`. The URLs are `servlet:`-relative and `@Uri`-annotated so
every response serializer resolves them against the current request.

`AsyncJobRegistry.create()` throws `IllegalStateException` when the concurrency cap is reached; `tryCreate()`
returns an empty `Optional` instead.
`create(IdempotencyKey)` and `tryCreate(IdempotencyKey)` return the existing job for a key that is already
registered, including a finished one within its retention window, so a double-click or retry collapses to one job.

## Security properties

- **The job id is the access control.** It is a 256-bit `SecureRandom` value, hex-encoded. A browser `EventSource`
  cannot set a CSRF header, which is why the id must be unguessable rather than CSRF-gated. An unknown id is
  indistinguishable from any other miss, so the id space cannot be enumerated. Treat the stream URL as a secret.
- **The caps are enforced on the server.** `AsyncJobRegistry.MAX_CONCURRENT_JOBS` is 8, the hard per-job timeout
  `AsyncJobRegistry.HARD_TIMEOUT` is 120 seconds (configurable through the `AsyncJobRegistry(Duration)`
  constructor), each job caps its streamed output at `AsyncJob.maxOutputBytes()` and its concurrent subscribers at
  `AsyncJob.maxSubscribers()`. A job over its output cap is terminated with a failure.
- **Single process.** Job state lives in the process heap. A restart drops every in-flight job, exactly as it
  invalidates every CSRF token.
- A job whose timeout fires or that is cancelled after it had an effect reports `cancelled-after-effect`; call
  `AsyncJob.markEffectStarted()` when the irreversible part begins so the outcome is reported truthfully.

See [Row Actions and Bulk Mutation](/docs/topics/RichTableViewsActions) for `ActionResult` and `IdempotencyKey`.
