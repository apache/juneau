This is the end-to-end tutorial for adding a page to an admin console built on Juneau: a resource that serves the
chrome, a navigation tree, a sortable and searchable table backed by a server-side data endpoint, and a test that
pins the page contract. The example is a pet inventory page; substitute your own bean.

The reference pages cover each piece in depth. Read them when a step here raises a question.

- [Admin-Console Chrome](/docs/topics/AdminConsoleChrome): directives, themes and the page contract.
- [Rich Table Views](/docs/topics/RichTableViews): what a table card can do.
- [DataTables Server-Side Processing](/docs/topics/DataTables) and [BeanQuery](/docs/topics/JuneauCommonsBeanQuery):
  the data endpoint.

## What you are building

A console page is four cooperating parts:

| Part | Provided by |
|---|---|
| The chrome template (header, navigation, footer) | `<@console>` and `<@navigation>` in one shared FreeMarker template. |
| The page template (its cards) | `<@page>` with one or more `<@card>` elements. |
| The data endpoint | A REST operation returning `DataTablesResults<T>`, backed by BeanQuery. |
| The assets (CSS, JavaScript) | The mixins `ConsoleChromeMixin`, `ViewsMixin` and `DataTablesMixin`. |

`<@page>` is the outermost directive in a page template. It captures its body (the cards), then includes the chrome
template, which must contain `<@console>`. The server never renders the chrome as HTML; it writes a JSON page
contract into the document and the shell script `juneau-console.js` draws the header, navigation, cards and footer
in the browser.

## Step 1: Dependencies

```xml
<dependency>
    <groupId>org.apache.juneau</groupId>
    <artifactId>juneau-rest-server-console-ui-freemarker</artifactId>
    <version>${juneau.version}</version>
</dependency>
<dependency>
    <groupId>org.apache.juneau</groupId>
    <artifactId>juneau-rest-server-views</artifactId>
    <version>${juneau.version}</version>
</dependency>
<dependency>
    <groupId>org.apache.juneau</groupId>
    <artifactId>juneau-rest-server-datatables</artifactId>
    <version>${juneau.version}</version>
</dependency>
```

The module table in [Admin-Console Chrome](/docs/topics/AdminConsoleChrome) explains what each one adds.
`juneau-rest-server-datatables` is optional, but you need it for any server-mode table, which is the common case.
jQuery and the DataTables library are not included in any of these; your page loads them itself.

## Step 2: The host resource and its mixins

The host resource composes every asset-serving mixin. Each one serves scripts and stylesheets relative to the
resource's own path, so all three must be on the resource that serves the page.

```java
@Rest(
    path="/console",
    mixins={
        FreemarkerMixin.class,        // renders .ftlh views
        ConsoleChromeMixin.class,     // chrome.css, theme CSS, juneau-console.js
        ViewsMixin.class,             // the views toolkit scripts and CSS
        DataTablesMixin.class         // juneau-datatables.js
    }
)
public class PetConsole extends BasicRestServlet {

    @Bean
    public FreemarkerMixin freemarker() {
        // Typed as FreemarkerMixin: the return type is load-bearing.
        return ConsoleFreemarkerMixin.create()
            .basePath("/templates/")
            .chromeTemplate("console/chrome.ftlh")
            .build();
    }

    @RestGet(path="/pets")
    public View pets() {
        return FreemarkerView.of("console/pets.ftlh");
    }
}
```

:::warning Compose DataTablesMixin
The `views` toolkit pack lists `juneau-datatables.js` ahead of `juneau-views.js` whenever a page has a server-mode
table. `DataTablesMixin` is what serves that script. If the host omits it, the table fails loudly in the browser
console and no rows load. See [Rich Table Views](/docs/topics/RichTableViews#modules-and-mixins).
:::

To set a theme for the whole console, build the mixin with `ConsoleChromeMixin.create().theme("gray").build()`,
or pick one per page with `<@console theme="gray">`.

## Step 3: The chrome template

One template holds the chrome and is shared by every page. It contains `<@console>` exactly once, with the
navigation tree and `<@main/>`, which marks where each page's cards go.

```ftl
<#-- templates/console/chrome.ftlh -->
<@console brand="Pet Store Console" chrome="true">
  <@navigation>
    <@node id="catalog" label="Catalog" href="/console/pets"/>
    <@node id="orders" label="Orders" href="/console/orders"/>
    <@node id="admin" label="Admin" visible=user.admin>
      <@node id="users" label="Users" href="/console/users"/>
    </@node>
  </@navigation>
  <@main/>
  <@footer text="Pet Store"/>
</@console>
```

Node ids must match `^[A-Za-z][A-Za-z0-9_-]{0,63}$`. Set `visible=` to a boolean to gate a node on a permission
check. The page names its active node with `<@page tab="catalog">`.

## Step 4: The page template with a table card

```ftl
<#-- templates/console/pets.ftlh -->
<@page tab="catalog" toolkit="views">
  <@card type="html">
    <h1>Pets</h1>
  </@card>
  <@card type="datatables" id="pets" title="Inventory">
  {
    dataUrl: '/console/pets/data',
    dataMode: 'server',
    defaultOrder: [[0, 'asc']],
    columns: [
      { key: 'name',   label: 'Name',   searchType: 'text' },
      { key: 'status', label: 'Status', searchType: 'enum' },
      { key: 'price',  label: 'Price',  searchType: 'numeric' }
    ]
  }
  </@card>
</@page>
```

- `toolkit="views"` asks for the views toolkit pack. The pack includes the DataTables glue only when the page has a
  server-mode datatables card.
- A `datatables` card requires an `id`, and its body is a JSON5 catalog with `dataUrl` and `columns`. Do not write
  a contract version in the catalog; the chrome stamps the current one.
- Besides `dataUrl` and `columns`, the chrome passes these catalog keys through: `copyLink`, `rowActions`,
  `rowClassRules` and `pausePollingWhileEditing` onto the view, and `selection` and `bulk` onto the slot.
- See [Catalog and Columns](/docs/topics/RichTableViewsCatalog) for every catalog key, the search types and the
  operator sets.

## Step 5: The data endpoint

The table's `dataUrl` points at a REST operation that takes the DataTables request and returns results. It runs the
request through BeanQuery.

```java
private final InMemoryBeanQueryContext<Pet> ctx = InMemoryBeanQueryContext.create(Pet.class).build();

@RestPost(path="/pets/data", parsers=JsonParser.class)
public DataTablesResults<Pet> petData(@Content DataTablesRequest req) {
    try (var s = ctx.getSession(petService.all())) {
        return DataTablesQuery.run(req, s);
    }
}
```

Restrict the operation to JSON with `parsers=JsonParser.class`. `DataTablesQuery.toBeanQuery` lets you add a guard,
such as a tenant filter, before the query runs. The full contract is in
[DataTables Server-Side Processing](/docs/topics/DataTables); the query language is in
[BeanQuery](/docs/topics/JuneauCommonsBeanQuery).

Because the table posts JSON, the state-changing checks of the loopback boundary apply if you use it; see
[Security Model](/docs/topics/RichTableViewsSecurity).

## Step 6: What the page loads, and in what order

You do not write the script tags. The parts of the order you can rely on:

1. The theme stylesheet comes first, then any `css=` stylesheets from `<@page>` and any `<@theme>` token overrides.
2. The toolkit pack scripts load in the pack's fixed order: renders, icons, search, pagestate, urlstate (shareable-URL state and the View Settings Copy link button), ribbon, the
   DataTables glue, views, config, regions, helpers. Full list on
   [JavaScript API](/docs/topics/RichTableViewsJavaScript).
3. Any `init=` scripts from `<@page>` load after the toolkit scripts, in the order given, and
   `<@scripts phase="after-toolkit">` content is placed immediately after the toolkit scripts.
4. The console shell, `juneau-console.js`, mounts the cards from the page contract. It hands a datatables card to
   `JuneauViews.regions.mount` on `DOMContentLoaded`, so the views scripts may load after it.

The load order is a contract: `juneau-views.js` must come before `juneau-regions.js`, and jQuery and DataTables
must be present before the glue runs. If you add your own scripts, list them in `init=` so they land after the
toolkit.

## Step 7: Test the page contract

Because the chrome exists only as the contract, assert on the contract rather than on rendered HTML.
`PageContractAssert` lives in `org.apache.juneau.rest.server.console.test` and has no JUnit dependency.

```java
import static org.apache.juneau.rest.server.console.test.PageContractAssert.*;

@Test void petsPage() throws Exception {
    var html = client.get("/pets").run().getContent().asString();
    assertPage(html)
        .isValid()
        .hasActiveNav("catalog")
        .hasCard("pets", "datatables");
}
```

Also lint your templates without rendering them:

```java
var findings = ConsoleTemplateValidator.create()
    .templateRoot(Path.of("src/main/resources/templates"))
    .chromeTemplate("console/chrome.ftlh")
    .validateAll();
assertTrue(findings.isEmpty(), findings::toString);
```

Set `ConsoleFreemarkerMixin.create().devMode(true)` while developing to validate every rendered contract against
the schema.

## Step 8: Common failures

A template mistake fails the render with an HTTP 500 and a message naming the directive and the fix. The usual
ones:

| Symptom | Cause |
|---|---|
| 500, "`<@card type=\"datatables\">` requires 'dataUrl' and 'columns'" | The catalog is missing one of them. |
| 500 naming the known paths | `<@page tab=...>` names a node that is not in the navigation. |
| 500, duplicate card id | Two cards share an `id`. |
| Blank table and a console warning about the DataTables glue | The host does not compose `DataTablesMixin`, or jQuery and DataTables are not loaded. |
| `.jc-console-error` banner in the browser | The contract failed a check in the shell, such as an unsupported page `version` or a missing template. |
