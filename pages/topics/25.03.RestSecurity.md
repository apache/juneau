Denial of service attacks can be alleviated through the <a href="/site/apidocs/org/apache/juneau/rest/server/Rest.html#maxInput()" target="_blank">maxInput()</a> setting.

Arbitrarily-large input will trigger an exception before causing out-of-memory errors.

The default value for this setting is 100MB.

Since the parsers do not use intermediate DOMs and instead parse directly into Java objects, deeply nested data
structures will almost always trigger stack overflow errors long before memory consumption becomes an issue.

However, this is NOT true of the RDF parsers, which build an intermediate DOM.

If parsing RDF, you may want to consider lowering the max-input value above.

## CSRF protection: loopback vs general

Juneau ships two request boundaries in `org.apache.juneau.rest.server.filter`. Both decide whether a state-changing
request came from a page your application served (or from a non-browser client) and refuse it when it came from
some other site's page. Neither one authenticates the caller, and neither proves the user meant the action; those
need their own mechanisms.

| Boundary | Use it when |
|---|---|
| `LoopbackBoundary` | The app is bound to the loopback interface and is reached under one pinned `Host` (for example `127.0.0.1:8790`) over plain HTTP. It pins that single origin and is the stricter of the two. |
| `CsrfBoundary` | Everything else: an app reached under a real host name, over HTTPS, behind a proxy, or under more than one name. Nothing is pinned; the request's own scheme and host are the expected origin. |

Both are applied by `RequestBoundaryFilter`. A rejected request is answered directly with a JSON body, a
`Cache-Control: no-store` header, and an `X-Request-Boundary` header naming the reason (for example
`ORIGIN_MISMATCH` or `CSRF_TOKEN_MISSING`). The request never reaches application code.

### What `CsrfBoundary` checks

On every state-changing request (the method is judged after any `?method=` or `X-HTTP-Method-Override` override, so
an override cannot carry a write past the checks):

- `Origin`, with `Sec-Fetch-Site` as a fallback, must match the request's own scheme, host and port. A literal
  `null` origin is refused.
- A browser request must also carry a synchronizer token in a request header (`X-Csrf-Token` by default). The
  token is read from that header and nowhere else: never a query parameter, never a form field.
- Origins are compared as normalized scheme, host and port. Default ports are equated (`https://app.example.com`
  and `https://app.example.com:443` match). IPv6 literals are compared in bracketed form exactly as sent, and
  nothing else is re-canonicalized, so two spellings of the same address do not match each other. That is
  deliberate: it fails closed.

### Registering the filter

```java
CsrfBoundary boundary = CsrfBoundary.create()
	.allowedHosts("app.example.com")
	.build();

servletContext.addFilter("csrf", new RequestBoundaryFilter(boundary))
	.addMappingForUrlPatterns(EnumSet.of(DispatcherType.REQUEST), false, "/*");
```

- Map the filter at `/*` so nothing can be reached around it.
- Register it for `REQUEST` dispatches only. An `ERROR` dispatch of a refused write can arrive without the token
  header and be refused in turn, replacing the error page with a 403, and a `FORWARD` to an HTML view looks like a
  page load and can create a session. The default registration in a servlet container, and Spring Boot's
  `FilterRegistrationBean`, is already `REQUEST` only.
- Register it ahead of any filter that acts on the request on the application's behalf. The one exception is
  described under proxies below.

By default the filter creates an HTTP session on a safe request that looks like a page load, so that the page it
serves can carry a session-scoped token. Turn that off with `createSessions(false)`.

### Reverse proxies and forwarded headers

By default (`OriginSource.HOST_HEADER`) the request's own origin is `request.getScheme()` plus the `Host` header.
`X-Forwarded-*` and `Forwarded` are never read, so a client cannot spoof them past the boundary.

Behind a proxy that terminates TLS, the scheme the app sees is `http` while the browser's `Origin` is `https`. Use
`OriginSource.CONTAINER` and configure the container's own forwarded-header support, so the container rewrites the
request before the boundary sees it:

| Stack | Setting |
|---|---|
| Jetty | Add a `ForwardedRequestCustomizer` to the connector's `HttpConfiguration`. |
| Tomcat | Add a `RemoteIpValve`. |
| Spring Boot | `server.forward-headers-strategy=native` rewrites before any filter runs, so filter order does not matter. |
| Spring Boot | `server.forward-headers-strategy=framework` registers `ForwardedHeaderFilter` at `Ordered.HIGHEST_PRECEDENCE`. Register the boundary's filter strictly later, never at `HIGHEST_PRECEDENCE` itself. |
| nginx | `proxy_set_header Host $host;` and `proxy_set_header X-Forwarded-Proto $scheme;` |

The boundary cannot see its own filter order. A misordered or misconfigured deployment shows up as `ORIGIN_MISMATCH`
refusals and a one-time warning in the log naming the likely cause (scheme-only or port-only mismatch).

Enable a forwarded-header customizer only behind a proxy that overwrites, rather than appends to, `X-Forwarded-*`.
A browser cannot send those headers, but anything that can reach the connector directly can, and the container then
trusts the forwarded host.

### WebSocket handshakes

A WebSocket upgrade is a `GET`, so the filter lets it through; the bus WebSocket endpoint applies the boundary to
the handshake itself. `BusWebSockets.register` accepts a bus whose `BusPolicy` boundary is a `LoopbackBoundary` or a
`CsrfBoundary`, and refuses to register for any other boundary type (it fails closed).

Under a `CsrfBoundary`:

- No token can be sent on a handshake, so the control is `Origin` plus `Sec-Fetch-Site`.
- The container's `checkOrigin` hook runs first. A missing, blank or `null` `Origin`, or one that is not a
  well-formed `http` or `https` origin, is refused with HTTP 403 before the upgrade.
- A well-formed `Origin` that is cross-site, or does not match the handshake's own origin, is refused after the
  upgrade: the connection is closed with code `4403` before any frame is sent and before any bus session is touched.
- The handshake has no server name, so the check always judges the raw `Host` header plus the scheme of the
  handshake's request URI, whatever `OriginSource` is set to. `ws` counts as `http` and `wss` as `https`.
- Behind a reverse proxy that rewrites `Host` to an internal name, with no container-side host rewriting, same-origin
  upgrades are refused. That is accepted behavior. Preserve the original `Host` at the proxy (in nginx,
  `proxy_set_header Host $host;`).
- Jetty's `ForwardedRequestCustomizer` rewrites the `Host` that both ordinary requests and the WebSocket handshake
  see, using `X-Forwarded-Host`. With it enabled the forwarded host is trusted for both, so the overwrite-not-append
  rule above applies to the WebSocket endpoint too.
- On Tomcat the handshake's request URI reports `ws` or `wss`, normalized as above. `RemoteIpValve` rewrites that
  scheme from `X-Forwarded-Proto`, so a TLS-terminating proxy works. It does not rewrite the `Host` header the
  handshake reads, even with the valve's `hostHeader` set to `X-Forwarded-Host`. Unlike Jetty's
  `ForwardedRequestCustomizer`, a forwarded host is therefore never trusted for the WebSocket endpoint, and the
  preserve-`Host` advice above applies.

### Non-browser clients

An unsafe request with neither `Origin` nor `Sec-Fetch-Site` is not from a browser page, and the policy set with
`nonBrowser(...)` decides what happens to it. With the default, `NonBrowser.ADMIT_NON_SIMPLE`, it is admitted without
a token only when a browser could not have sent it cross-site without a CORS preflight, which this boundary never
answers. For client authors the rule is: send JSON, or send `Origin` plus the token. Concretely, an unsafe request with no
`Origin` is admitted if its method is not `GET`, `HEAD` or `POST`, or if it carries exactly one `Content-Type` that is
not `application/x-www-form-urlencoded`, `multipart/form-data` or `text/plain`. Everything else is refused.

The alternatives are `NonBrowser.REJECT` (refuse every such request) and `NonBrowser.REQUIRE_TOKEN` (treat it like a
browser request and require the token). `requireJson(true)` additionally requires a single `application/json`
content type on every admitted write.

This relies on browsers sending `Origin` on every non-simple request they issue. Current browsers do, and the
`Origin` check is the real control for them.

### HTML forms are unsupported

A plain HTML `<form>` cannot set a request header, so every HTML form POST, including your own app's, is refused
with `CSRF_TOKEN_MISSING`. `CsrfBoundary` is for applications whose writes go through script that sends the token
header (the Juneau views toolkit already does). The token is not accepted as a form field or query parameter on
purpose: that would put it in URLs, logs and `Referer` headers.

### Tokens, sessions and cookies

The default token strategy, `CsrfTokens.perSession()`, derives one token per session id (an HMAC of the id under a
per-process key), so a visitor who loads the page learns only their own token. `CsrfTokens.perProcess()` uses one token for the whole process; any
visitor can read it, so in a multi-user app it adds little beyond the `Origin` check. In a cluster, give every node
the same key so any node accepts any node's token.

Because a per-session token follows the session id, the application must:

- call `request.changeSessionId()` on login, or a token seen before login stays valid after it;
- mark the session cookie `HttpOnly` and `SameSite`, and not scope it to a parent `Domain`;
- not use URL rewriting for session ids.

The boundary never changes a session id and never sets cookie attributes; those stay the application's.

The value written into a page is masked under a fresh pad on every embed. Masking defends only against BREACH-style
compression oracles; anyone who can see the wire value can unmask it. Never log the token header.

### Pages that embed a token

Any code that stamps a token into a response must call `RequestBoundaryFilter.markTokenBearing(response)` before it
writes the first byte of the body. It replaces `Cache-Control` with `private, no-store`; without it a shared cache can
serve one session's token to another session. This applies to a view host that uses `ViewTable.CSRF_ATTR` or
`RegionTable.of(region, csrfToken)`, and to `PageSpec.csrf(...)`. The console page chrome does it for you.

A token is never embedded into a response that is already committed, because the response can no longer be
marked. That includes `csrf` attributes an author put on the page's body element. The page still loads, and its
writes then fail visibly for want of a token.

### DNS rebinding and CORS

A rebound page's `Origin` and `Host` agree, so origin checking alone does not stop DNS rebinding. TLS defeats it. A
plain-HTTP intranet app should list its host names with `allowedHosts(...)`; the boundary then refuses any request,
safe ones included, whose own host is not listed, with 421.

`CsrfBoundary` does not support cross-origin callers and adds no `Access-Control-Allow-*` headers. Do not put an
origin-reflecting CORS layer in front of it: reflecting every `Origin` back undoes the check.
